> **For Hermes:** Use the subagent-driven-development skill to carry out this

> **Definition of done (ADR 0007):** a task that touches behaviour isn't
> done until an e2e spec covers it and passes locally and in CI.

**Goal:** a client's team reviews one real project of ours through c11n
(invite → magic link → comment → reply → resolve), hosted on k8s, with no
change to the client project's code.

**Architecture:** this is unchanged from the reboot and recorded in
`docs/adr/`:

- Caddy injects the overlay and is also the security boundary (0002).
- PocketBase is the backend, with server-side logic in JS hooks (0003).
- The overlay is Vue 3 in a shadow DOM (0004).
- One pod per reviewed site, deployed with Helm (0005).
- Identity is a passwordless magic link, held in an httpOnly cookie that
  the proxy checks (0006).

**Tech stack:**

- Caddy 2.11 with `replace-response`
- PocketBase 0.39.x and the matching JS SDK
- Vue 3, Pinia, Vite, Vitest
- Playwright for e2e
- Helm 3, k3s (closedcloud) for verification
- GitHub Actions on Blacksmith runners

**Baseline:** see `docs/assessment/2026-11-25-state-of-the-repo.md`. In
short, `main` is green in CI but broken at runtime (B1–B4, S1–S4).

## Phase 1: Full-stack e2e harness (definition of done)

**Branch:** `feature/e2e-harness`. **PR:** "e2e harness: real
Caddy+PocketBase+demo+Chromium, red on known bugs".

**Outcome:** `npm run e2e` starts the real stack from native binaries and

**Deviations (recorded at implementation):**

- The B2 fix moved into Phase 1: no comment-flow e2e could run while the
  hook deadlocked, so the hook had to be fixed for the harness to be green.
  The race-free version uses a `comment_counters` table (write lock first)

- 1.7 runs the fixtures as separate invocations (`npm run e2e:vite`,

- CI runs `npm test -w e2e` once per matrix leg (`C11N_FIXTURE` from the
  matrix), not `npm run e2e`, which would run both fixtures in one job.

### Task 2.2: B2, the `seq` hook deadlock — ✅ done in Phase 1

**Status: done in Phase 1** (commits `f594b54`, `7257655`), moved forward
because the harness could not exercise the comment flow while the hook
deadlocked. The shipped version differs from the snippet below: the
`SELECT MAX(seq) + 1` read takes no write lock and lost the B2b race
(400 `validation_not_unique` under parallel creates), so it was replaced by
a `comment_counters` row that is upserted first (write lock, then read).
That migration is `1764000100_comment_seq_counters.js`; the counter row
cascades with its project.

**Files:**
- Modify: `deploy/pocketbase/pb_hooks/comments.pb.js`

This replacement was verified on PocketBase 0.39.11 on 2026-11-25: 3
sequential creates plus 10 concurrent ones gave seqs 1..13, all unique, no
hang.

```js
// Assign a monotonic per-project `seq` inside the create transaction.
// onRecordCreateExecute runs inside the request's transaction; use e.app
// (the tx-bound app). NEVER nest runInTransaction here, because that
// deadlocked SQLite (B2).
onRecordCreateExecute((e) => {
  const row = new DynamicModel({ maxSeq: 0 })
  e.app.db()
    .newQuery("SELECT COALESCE(MAX(seq), 0) AS maxSeq FROM comments WHERE project = {:project}")
    .bind({ project: e.record.get("project") })
    .one(row)
  e.record.set("seq", row.maxSeq + 1)
  e.next()
}, "comments")
```

Also ignore any client-supplied `seq` on create. The hook overwrites it
anyway; add an e2e assertion that proves this.

**Verify:** the B2 spec passes. Add an e2e spec that fires 10 parallel API
creates and checks seqs 1..10 are unique.

**Commit:** `fix(pocketbase): seq hook in create tx, no nested transaction (B2)`

**Phase 3 exit:**
- The full flow passes in e2e: owner invites team, team invites client,
  client signs in by link, comments, and team resolves.
- No password exists anywhere.
- `docs/quickstart.md` is rewritten around invites.

**Deviations (recorded at implementation):**

- **72 h links, not 15 min.** The task table's 3.4 says 15 minutes; the
  as-built default is `C11N_LINK_TTL_HOURS=72`, because the MVP is
  copy-the-link over Slack/email and a 15-minute link is unusable by hand.
  Re-inviting revokes the older unused links (M7), and the invite route is
  quota-limited per inviter (`C11N_INVITE_RATE_PER_HOUR`, M6), so the longer
  window is bounded.
- **The token is in the fragment and the claim is a POST.** The table's 3.4
  describes `GET /__c11n/auth/magic?t=&next=` claiming on the GET. That let
  any unfurler (Slackbot, Outlook Safe Links) burn the invite before the human
  clicked it, and put the token in PocketBase's request log. Links are now
  `/__c11n/auth/#t=…` (never sent to a server), the page drops the fragment on
  read, and the single-use claim is a JSON POST with Origin /
  Sec-Fetch-Site checks.
- **Bootstrap uses `routerUse`, not `onServe`.** `bootstrap.pb.js` cannot hook
  `onServe` in the JSVM (not exposed there); it registers the one-time owner
  bootstrap through `routerUse` instead.
- **Logout signs out everywhere.** 3.6 only asks for clearing the cookie; the
  as-built route also rotates the user's `tokenKey`, so a copied cookie dies
  with the session. That is deliberately stronger than the task.
- **Invite quota.** 3.3 did not ask for one; a per-inviter hourly cap was
  added (M6) so one compromised owner/team account cannot mint an unbounded
  pile of 72-hour links. Superusers are exempt (break-glass/CLI).
- **PocketBase's auth endpoints are blocked at the proxy.** `/__c11n/pb/*`
  answers 403 to `auth-refresh`, `auth-with-password`, `impersonate/…` and the
  rest of PocketBase's token-minting routes (I-1). The overlay uses none of
  them; without the block, any page script could POST `auth-refresh` and read
  a bearer token out of the JSON body, defeating the httpOnly cookie.
- **The reviewed app is cut off from the session cookie.** Caddy strips only
  `c11n_session` from the upstream `Cookie` header and renames an upstream
  `Set-Cookie: c11n_session=…` to `c11n_blocked=…` (I-2). Identity still
  reaches the app as `X-C11n-User` / `X-C11n-Role` (id and role, no
  credential) — documented in ADR 0002 as an intentional interface.

## Phase 4: Proxy hardening for the dogfood site (needs Q1, the repo)

**Known up front:** the app is a Vue 3 SPA served by Go in production and
by Vite in dev. Task 1.7 already proves the generic version of both
topologies. This phase runs the same checks against the **real** app, in
both modes.

**Branch:** `feature/proxy-hardening`.

First, run the **compatibility probe**. This is a scripted e2e spec,
`e2e/specs/upstream-compat.spec.ts`, run with `C11N_UPSTREAM` set to the
real staging URL. It loads the 5 most important routes and checks:

- the overlay is injected
- there are no console errors that aren't there without the proxy
- the user stays on the review host after redirects
- the app's API calls succeed
- the app's auth, if it has any, works

Then fix only what the probe finds. These are the candidate fixes, each
added only if the probe shows the problem:

| Symptom | Fix |
|---|---|
| Vhost 404 or wrong site | `header_up Host {upstream_hostport}` |
| Redirects leave the review host | `header_down Location` rewrite from the upstream origin to `{http.request.scheme}://{http.request.host}` |
| Cookies don't stick | `header_down Set-Cookie` rewrite that strips `Domain=` |
| `<meta>` CSP blocks the overlay | `replace` rule that removes the `http-equiv="Content-Security-Policy"` meta |
| A service worker serves pages without the overlay | inject an unregister snippet, or answer the SW script path with 404 |
| Cross-origin API CORS rejects the review host | add the review host to the staging API's allowlist. This is a config change on the client side, not a code change; get Tom's OK first |
| OAuth redirect URI mismatch | register the review host as an extra redirect URI. Same: config, not code |
| Upstream compresses even with `Accept-Encoding: identity` | add `encode` handling, or decompress in Caddy |

**Exit:** the compat spec passes against the real staging site in CI. The
staging URL goes in a CI secret; this job is not required on forks.

## Phase 8: The dogfood run

1. Deploy to the client's review host. This is a Phase 5 release, with the
   Phase 4 config applied.
2. Owner (Tom) invites our team, and the team invites the client's
   reviewers.
3. Run a 2-week review cycle on the real project.

**Track:**
- invites sent and accepted
- comments, replies and resolutions
- orphaned pins (anchors that no longer resolve)
- errors, from Caddy and PocketBase logs plus the overlay
  `console.error` beacon (add one in Phase 6)
- a 5-question feedback form for the client's team at the end

**Success criteria (all of them):**
- every invited client user signs in without our help
- no lost comments
- no proxy breakage on the reviewed routes
- under 10% orphaned pins across deploys
- the client's team uses it for the whole cycle, rather than going back to
  email

Write up the run as `docs/assessment/<date>-dogfood-retro.md`. It drives
the next plan.

## Risks

| Risk | Mitigation |
|---|---|
| The dogfood site has origin-sensitive auth or APIs we can't reconfigure | Phase 4's probe comes **before** Phase 5 effort; it escalates to Tom with options |
| SMTP isn't available | the copy-the-link fallback (3.3) |
| Selector anchors break across client redeploys | the orphan list is visible; track the rate in Phase 8; text-fallback tuning is next |
| A same-origin script in the reviewed app misuses the session | documented, accepted residual risk (ADR 0002); the httpOnly cookie prevents token theft |
| SQLite on network storage | use a RWO block-storage PVC, never NFS; noted in the runbook |
| The e2e suite is slow or flaky | single worker, fixed ports, pidfile teardown, no retries, so flakes show up instead of being hidden |

## Validation summary

- **Unit (vitest):** fast logic coverage, as today.
- **e2e (Playwright on the native stack):** required in CI. It covers the
  core flow, permissions and the Caddyfile config matrix.
- **k8s:** Helm install on ephemeral k3s plus the same e2e suite (Phase 5).
- **Real world:** the upstream compat spec against the dogfood staging site
  (Phase 4), then the dogfood run itself (Phase 8).
